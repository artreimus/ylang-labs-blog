Most APIs assume a developer will fill in the gaps. An agent can often infer the missing step, but every inference adds another chance to retry, burn tokens, or fail the task.

If a tool hides its mutation semantics, returns the backend object unchanged, or reports an error without a repair path, the model has to guess. Those guesses show up as retries, tokens, latency, and failed tasks.

That is why the next API fight is not REST versus GraphQL. It is whether the interface makes the next correct action obvious to a model.

## A valid call can still be the wrong operation

Imagine an agent deploying a new image for `checkout-api`. The available tool is `update_service(service_id, data)`, and the model sends a schema-valid payload:

```json
{
  "service_id": "checkout-api",
  "data": {
    "image": "registry.example/checkout@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  }
}
```

The call is valid, but the interface has left the dangerous decisions implicit. Does `data` patch the service or replace it? If the request times out, can the agent retry without creating a second deployment? If another release changed the service first, will this call overwrite it?

The model chose a reasonable payload. The API did not give it enough information to act safely.

Humans bridge awkward interfaces by reading documentation, interpreting prose, and copying the right identifier. An agent repeats that inference inside every tool loop. A good agent-facing API removes as much of that hidden judgment as it can.

## A schema can reject mistakes without teaching the next move

Across OpenAI, Anthropic, and MCP, tool contracts expose a name, model-facing description, and typed input schema.

Enforcement matters. Declaring JSON Schema alone cannot prevent invalid calls. OpenAI's strict mode requires `additionalProperties: false` on every object and all properties marked as required, with nullable types when a field is optional.

Descriptions help the model choose between tools. MCP's `inputSchema` and optional `outputSchema` make the input and structured result explicit.

But validity only solves the shape of the call.

For the deployment example, replace the generic update with an operation such as `deploy_release(service_id, image_digest, expected_version, idempotency_key)`. Each field removes a decision the model would otherwise have to infer.

The error contract matters too. A version conflict should return the current version and tell the caller to read the service before retrying. A timeout should say whether the idempotency key can be reused. "Request failed" does neither.

## The result payload is part of the API

Input schemas get more attention than output shape, but multi-step work depends on what the model can do after a tool returns.

After `deploy_release`, return the fields the next call needs: `deployment_id`, `service_id`, `status`, `observed_version`, and the allowed next actions. The agent can now call `deployment(action, deployment_id)` with `status` or `cancel` instead of searching a raw cloud response for identifiers.

Do not return build logs, image metadata, service configuration, and provider diagnostics by default. Make that detail available through a separate inspection call when the deployment fails.

The same rule applies to CLIs. A `deployctl release --help` page should explain the required image digest, version precondition, idempotency key, JSON output mode, and exit codes. The command should carry enough information for an agent to construct a safe call without searching a separate guide.

## Put policy in the operation, not the prompt

The best agent-facing interfaces make the next legal move obvious. Before exposing a tool, ask five questions:

1. Can the model choose the operation from its name and description?
2. Can the schema reject fields and values the operation does not support?
3. Does the mutation say what changes and whether repeated execution is safe?
4. Does the result return the identifiers and evidence needed for the next call?
5. Does each expected failure explain how to repair or abandon the call?

Do not split every endpoint into its own tool. A larger tool surface creates another selection problem, so related operations often belong in one tool with an explicit action parameter.

For common or high-risk work, expose a small set of domain actions that state the rules clearly. Keep a generic request as an escape hatch for the long tail, but do not make it the easiest way to perform a destructive mutation.

## Run the same deployment tasks before and after the change

Build a fixed set of tasks around the old and new interfaces: deploy a release, retry after a timeout, recover from a version conflict, inspect a failed deployment, and cancel one in progress. Run the same agent and model settings against both versions.

Compare completion rate, validation failures, retries, end-to-end latency, token cost, and human intervention. Do not stop at fewer schema errors. The new interface should also reduce repair calls and help more runs reach the intended deployment state.

Agents do not replace the human-facing API. They add a caller that selects and chains actions under uncertainty. If the deployment tasks do not succeed more often or with less repair work, the interface is tidier, but not better.
