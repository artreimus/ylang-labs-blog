Most APIs assume a developer will read the documentation and fill in any missing steps. An agent-facing API gives that job to an AI model. The model has to choose and chain calls from the tool name, its description and accepted inputs, and the previous result.

When those clues are vague, the agent has to guess. It may repeat a call, use more tokens, add latency, or fail the task.

That is why the next API fight is not REST versus GraphQL. It is whether the interface makes the next safe action obvious to a model.

## A valid call can still be the wrong operation

Imagine an agent deploying a new image for `checkout-api`. The available tool is `update_service(service_id, data)`, and the model sends a payload that matches the schema:

```json
{
  "service_id": "checkout-api",
  "data": {
    "image": "registry.example/checkout@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  }
}
```

The call is valid, but the interface has left the dangerous decisions implicit. Does `data` patch the service or replace it? If the request times out, can the agent retry without creating a second deployment? If another release changed the service first, will this call overwrite it?

The model chose a reasonable payload. The API did not give it enough information to act safely.

Humans repair awkward interfaces by reading documentation, interpreting prose, and copying the right identifier. An agent has to repeat those judgments at every step. A good agent-facing API removes as much of that guesswork as it can.

## A schema can reject mistakes without teaching the next move

Across OpenAI, Anthropic, and MCP, tool definitions include a name, a description for the model, and a typed input schema.

A JSON Schema describes valid arguments, but non-strict tool calling can still produce arguments that do not match it. OpenAI's strict mode enforces schema adherence. It requires `additionalProperties: false` on every object and every property to be marked as required. Optional fields use a nullable type.

Descriptions help the model choose between tools. MCP's `inputSchema` and optional `outputSchema` make the input and structured result explicit.

But validity only solves the shape of the call.

For the deployment example, replace the generic update with `deploy_release(service_id, image_digest, expected_version, idempotency_key)`. The operation name says what it does. `expected_version` rejects the call if another release has already changed the service. `idempotency_key` lets a retry refer to the same deployment instead of starting a second one.

Errors should also tell the agent what to do next. If the service version has changed, return the current version and tell the caller to read the service before retrying. If the request times out, say whether the same idempotency key can be reused. "Request failed" does neither.

## The result payload is part of the API

Input schemas get more attention than output shape, but multi-step work depends on what the model can do after a tool returns.

After `deploy_release`, return the fields the next call needs: `deployment_id`, `service_id`, `status`, `observed_version`, and the allowed next actions. `observed_version` tells the caller which version of the service the deployment actually used. The agent can now call `deployment(action, deployment_id)` with `status` or `cancel` instead of searching a large cloud response for identifiers.

Keep the default result focused. Return the deployment identifier, current state, and possible next actions. Make build logs, image metadata, service configuration, and provider diagnostics available through a separate inspection call when the deployment fails.

The same rule applies to CLIs. A `deployctl release --help` page should explain the required image digest, how `expected_version` prevents stale updates, when an `idempotency_key` can be reused, the JSON output mode, and the exit codes. The command should carry enough information for an agent to construct a safe call without searching a separate guide.

## Put safety rules in the tool, not the prompt

The best agent-facing interfaces make the next safe move obvious. Before exposing a tool, ask five questions:

1. Can the model choose the operation from its name and description?
2. Does the tool validate its arguments and reject unsupported fields or values?
3. Does the operation say exactly what changes and whether a retry is safe?
4. Does the result return the identifiers and evidence needed for the next call?
5. Does each expected failure explain the next move or when to stop?

Do not decide by endpoint count alone. Split an operation when combining it would hide different inputs, side effects, or retry rules. Starting a release deserves `deploy_release(...)` because it creates a deployment and needs a current-version check and a safe-retry key.

Related follow-up actions can share `deployment(action, deployment_id)` only when each action's behavior and safeguards remain explicit. For example, `status` can be read-only, while `cancel` must be marked as destructive and may require confirmation or an expected state. If one tool cannot make that distinction obvious, split the actions into separate tools.

Keep a generic request tool for uncommon cases, but do not make it the easiest way to perform a destructive change.

## Run the same deployment tasks before and after the change

Build a fixed set of tasks around the old and new interfaces: deploy a release, retry after a timeout, recover from a version conflict, inspect a failed deployment, and cancel one in progress. Run the same agent and model settings against both versions.

Compare completion rate, validation failures, retries, end-to-end latency, token cost, and human intervention. Do not stop at fewer schema errors. The new interface should also reduce repair calls and help more runs reach the intended deployment state.

Agents do not replace the human-facing API. They add a caller that selects and chains actions under uncertainty. If the deployment tasks do not succeed more often or with less repair work, the interface is tidier, but not better.
