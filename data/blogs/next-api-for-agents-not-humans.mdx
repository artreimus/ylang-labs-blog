The next API fight is not REST versus GraphQL. It is whether the interface works for agents as well as humans.

Agents call tools, inspect partial results, repair failures, and choose the next step from the interface response.

When that interface was designed only for a human scanning docs or a terminal, the mismatch burns retries, tokens, and time. Tool design is now an API-design problem.

## Good enough for humans is not good enough for agents

Developers can skim a wall of CLI help or provider-shaped JSON, infer the right flag, and copy the next ID. When an interface leaves that judgment implicit, the model has to infer it again.

Armin Ronacher documented a newer Claude model producing a correct edit but inventing fields in a nested schema, which forced Pi's harness to reject and retry the call.

The question is how many retries, repair calls, tokens, and seconds the model burns before it succeeds.

## Schema enforcement is the floor, not the interface

Across OpenAI, Anthropic, and MCP, tool contracts expose a name, model-facing metadata, and a typed input schema.

Provider enforcement matters. Declaring JSON Schema alone cannot prevent invalid calls. OpenAI's strict mode requires `additionalProperties: false` on every object and all properties marked required, with nullable types for optional fields.

A good description can help the model choose between tools. MCP's `inputSchema` and optional `outputSchema` make input and structured-output contracts explicit.

But a valid call can still be a bad interface.

`update(id, data)` can be schema-valid and still hide the object's allowed fields, patch semantics, validation errors, conflicts, and next action. It is type-checked ambiguity.

Agent-facing APIs need narrower names, parameter vocabulary that matches the task, enums where the choice space is small, and error messages that tell the model what to change.

## The result payload is part of the API

Input schemas get more attention than output shape, but multi-step work depends on what the model can do after a tool returns.

A search tool rarely needs the full backend object. A ranked list with `issue_id`, `title`, `why_matched`, `url`, and `next_actions` is smaller and carries what the next step needs: evidence, identity, and constrained actions.

The same idea applies to CLI output. A human-oriented `--help` page can be generous with prose. An agent-oriented CLI should also expose parseable output, documented exit codes, stable IDs, and examples an agent can follow.

Willison demonstrated this with `shot-scraper video`: a coding agent read the command's `--help`, wrote a YAML storyboard, and recorded a browser demo. The help page was effectively part of the tool contract.

## Design for the next legal move

The best agent-facing interfaces make the next legal move obvious. Five surfaces deserve API-design attention:

1. **Tool names and descriptions:** Make selection cheap. Say what the tool does, when to use it, and when not to use it.
2. **Input schemas:** Constrain the choice space. Prefer precise fields, enums, and domain language over generic blobs.
3. **Mutation semantics:** Say whether a call patches, replaces, retries safely, or destroys state. Use preconditions or idempotency keys where duplicate execution would be costly.
4. **Result payloads:** Return compact evidence, stable identifiers, cursors, and action hints.
5. **Failure messages:** Explain the repair. Tell the model which field was wrong, what values are allowed, and whether retrying is safe.

Do not make every tool tiny. The standard is the smallest complete contract that preserves safety and the next step.

For example, replace `github_request(method, path, body)` with task-shaped operations such as `issue_search(...)`, `issue_comment(..., idempotency_key)`, and `pull_request_review_threads(...)`. A generic tool can hide policy decisions; task-shaped tools can make them explicit.

## Measure the interface, not the vibes

Agent-facing API design should leave a measurable trail. Before and after changing a tool surface, compare retries, validation errors, repair calls, latency, token cost, task completion, and human intervention.

Willison's DSPy work tested prompt changes against real Datasette tools and custom metrics. Apply that discipline to interfaces: if a result adds `next_actions`, measure task completion and repair calls; if one generic mutation becomes three specific tools, track selection errors.

## Agent APIs are product surfaces now

For years, API design meant designing for developers. Clear docs, stable endpoints, predictable errors, and useful examples were the standard.

Agents do not remove the human-facing API. They add a caller that chooses and chains actions under uncertainty.

Treat that boundary as a product surface: enforce schemas, make mutations explicit, return continuation state, and preserve enough evidence to debug the loop.

Then measure the result. If those metrics do not move in the right direction, a cleaner schema has not demonstrated a better interface.
