## Anthropic GLM-5.3 case study

Anthropic, [GLM-5.3 and the spread of advanced cyber capabilities](https://www.anthropic.com/research/glm-5-3-and-the-spread-of-advanced-cyber-capabilities), **2026-09-29**, accessed **2026-11-16**. The article’s two interactive charts use the report’s plotted values, not results from a Ylang Labs experiment.

Original figures, visually checked against the data arrays: [refusal and capability](https://assets.claude.com/30385675797a82dba572c10ffeefe734e1eb760c.jpg), [simulated engagement](https://assets.claude.com/14006409417e998005a3150ebadbc8276653851b.jpg). The recreated chart omits the source’s approximate 95% uncertainty intervals and identifies its values as rounded.

- Mean refusal: GLM-5.3 released approximately 95%, edited approximately 6%; GLM-5.3-Flash approximately 95% and 14%. These are rounded, equally weighted means across JailbreakBench, HarmBench, and StrongREJECT. The prose separately reports GLM-5.3’s post-edit refusal of approximately 3%, 2%, and 12% respectively; these are not the chart’s mean values.
- Capability figure: GLM-5.3 GPQA-Diamond 88% → 88%, CyberGym 85% → 81%; Flash GPQA-Diamond 89% → 89%, CyberGym 86% → 86%. Values are read from the source figure. GPQA-Diamond uses 198 questions with four samples each; the CyberGym subsets contain 185 tasks for GLM-5.3 and 95 for Flash. These are different subsets, so the article does not rank the two models from these figures.
- Simulation: GLM-5.3 attempted a target connection in 0%, 64%, 92%, and 100% of trials under direct requests, deceptive cover story, reasoning prefill, and abliteration respectively. Each cell uses 50 samples: five orders × two targets × five attempts. The fake command tool does not execute code or access external systems; another model approximates its result. This measures attempted engagement, not working exploits, actual connections, or real-world attack success. Different requests and metrics explain why these values are not complements of benchmark refusal rates.
- Effort: the reported first GLM-5.3 attempt used about 2,200 GPU hours and $4,400 in computation, mostly variant search and evaluation. The approximately 600-hour/$1,200 figure is the authors’ estimate for an experienced team, not a second measured GLM-5.3 run or a universal cost. The article omits the separate measured Flash effort to keep this distinction clear.
- The report links the Arditi method but does not publish a complete GLM-5.3 layer/direction/calibration/export configuration. The numerical weight-edit example explains the general method, not an independently verified reconstruction of Anthropic’s procedure.
- GLM-5.3 in this report is a different model from the community GLM-4.7-Flash release in the table. Reported results are not attributed to that release.

Primary benchmark definitions:

- David Rein et al., [GPQA: A Graduate-Level Google-Proof Q&A Benchmark](https://arxiv.org/abs/2311.12022), 2023: expert-written multiple-choice science questions. The article introduces GPQA-Diamond as difficult science questions; it does not confuse the full collection with the 198-question evaluation described above.
- [CyberGym](https://www.cybergym.io/cybergym/), [paper](https://arxiv.org/abs/2506.02548), 2025: reproducing real software vulnerabilities from source code and a description. A generated test should trigger the bug before its patch and not afterward. It is not described as a vulnerability-repair benchmark or equated with the report’s separate ExploitBench results.

## Practical walkthrough: Heretic 2.1.0

Checked **2026-11-16** against the [2.1.0 release](https://github.com/p-e-w/heretic/releases/tag/v2.1.0), published **2026-11-08**, and its versioned sources. The walkthrough supplies an executable workflow; no GPU search, model download, or modified-checkpoint evaluation was performed for this article.

- [Tagged README](https://github.com/p-e-w/heretic/blob/v2.1.0/README.md) and [package metadata](https://github.com/p-e-w/heretic/blob/v2.1.0/pyproject.toml): `heretic-llm==2.1.0`, `heretic MODEL_ID`, Python minimum 3.10, and README requirement for hardware-appropriate PyTorch 2.6+. The article chooses Python 3.11+ to accommodate the current [PyTorch installation guidance](https://pytorch.org/get-started/locally/), with a Linux/NVIDIA example and a GPU-availability check. The [official tutorial](https://heretic-project.org/tutorial) supplies the environment, accelerator, and memory prerequisites; no time or memory guarantee is extrapolated from its default-method example.
- [Versioned configuration](https://github.com/p-e-w/heretic/blob/v2.1.0/config.default.toml) and [configuration loader](https://github.com/p-e-w/heretic/blob/v2.1.0/src/heretic/config.py): defaults choose Arbitrary-Rank Ablation, so the article explicitly selects `heretic.modifiers.abliteration.Abliteration` through `config.toml` in the working directory. Unspecified settings retain their defaults.
- [Abliteration implementation](https://github.com/p-e-w/heretic/blob/v2.1.0/src/heretic/modifiers/abliteration.py): `orthogonalize_direction = false` avoids the extra adjustment against the harmless mean; `row_normalization = "none"` disables additional row-magnitude rescaling. The direction is still normalized and projection-based edits still occur. The program searches directions and layer/component strengths. This parameterized implementation is not described as exactly reproducing the original all-residual-writing-path intervention or Anthropic’s unpublished GLM configuration.
- Default scorers count keyword matches and compare first-token distributions on harmless prompts. [KeywordRate](https://github.com/p-e-w/heretic/blob/v2.1.0/src/heretic/scorers/keyword_rate.py) is not a complete harmful-compliance judge; [KLDivergence](https://github.com/p-e-w/heretic/blob/v2.1.0/src/heretic/scorers/kl_divergence.py) is not a general capability test. Data used to optimize/select edits must not be presented as an independent final evaluation, even where the dataset split is named `test`.
- [CLI and export source](https://github.com/p-e-w/heretic/blob/v2.1.0/src/heretic/main.py): select a trial, choose the chat or local-save action, enter a directory, then choose full-model merge versus adapter-only export. A merged export writes model and tokenizer. Study checkpoints alone are not a standalone edited model. The guide selects a new local folder and does not instruct automatic publication.
- The Qwen3-4B-Instruct-2507 model is the tagged README’s example. The three huihui-ai examples elsewhere in the article are separate releases; their cards do not establish that they were produced using this workflow.
- The final comparison uses the [Transformers pipeline API](https://huggingface.co/docs/transformers/main_classes/pipelines#transformers.TextGenerationPipeline), checked against [5.18.0 source](https://github.com/huggingface/transformers/blob/v5.18.0/src/transformers/pipelines/text_generation.py) and [pipeline factory](https://github.com/huggingface/transformers/blob/v5.18.0/src/transformers/pipelines/__init__.py). A model identifier or local merged-model folder is accepted. Chat messages use the tokenizer’s template; `return_full_text=False` returns newly generated text as a string. The same script runs each model in a separate process against the same user-supplied `heldout.txt`, avoiding simultaneous model residency. Greedy decoding and the same token cap keep the comparison settings matched; this is a manual inspection workflow, not a new measured benchmark result.

## Teaching approach and explanatory boundaries

- Lead with published refusal and selected-capability evidence, then ask how the same model can change its willingness more than its measured task performance. Explain how lists of numbers affect later layers’ next-token predictions before adding technical terms.
- Activations vary with the input; weights ordinarily remain fixed during generation. Changing temporary activations and editing saved weights are different ways to intervene.
- One original invented component uses the weight grid `[[1, 2], [3, 4]]`. Input `(1, 1)` gives `(3, 7)`: `1×1 + 2×1 = 3`, `3×1 + 4×1 = 7`. Removing its vertical component gives `(3, 0)`.
- Editing the grid to `[[1, 2], [0, 0]]` produces zero in the second output for any input, while retaining the first output calculation. This makes the persistence of a saved edit concrete. These are not measured model activations or real refusal neurons.
- The real direction can cross many coordinates. General weight orthogonalization must account for relevant residual-writing paths and initial representations, with architecture-specific details checked separately. The grid is not an architecture-independent recipe for modifying a checkpoint.
- The edit changes existing calculations; reduced refusal does not establish new knowledge, universally preserved capability, or correctness. Later research and Labonne’s reported degradation provide context for these limits.
- Proposed evaluation guidance is not a report of executed experiments. Harmful answers, unnecessary refusals, useful capability, and appropriate uncertainty require separate evidence.

## Follow-up: what is documented about the release methods

Checked **2026-11-16**. All three community model cards link to [Sumandora/remove-refusals-with-transformers](https://github.com/Sumandora/remove-refusals-with-transformers), but do not supply complete release-specific recipes.

- Qwen3-8B v2 claims a newer, faster ablation method and notes a layer-0 change to address garbled output. This does not identify every edited layer or reproduce the new algorithm.
- GLM-4.7-Flash identifies its source model and the reference implementation, without a model-specific calibration or edit configuration. A LoRA-related description in its usage script is not evidence of how the release was created.
- DeepSeek-R1-Distill-Qwen-32B identifies the already-distilled checkpoint as its starting point; its card does not give the full ablation configuration.
- The linked code was inspected at commit `7786b0a8c50f4e7c16a0e300e697b2876decc0c6`: [direction calculation](https://github.com/Sumandora/remove-refusals-with-transformers/blob/7786b0a8c50f4e7c16a0e300e697b2876decc0c6/compute_refusal_dir.py) compares harmful and harmless activation means; [inference](https://github.com/Sumandora/remove-refusals-with-transformers/blob/7786b0a8c50f4e7c16a0e300e697b2876decc0c6/inference.py) removes the selected component during generation. This demo does not show production of the three downloadable weight checkpoints. Its defaults must not be attributed to those releases without further evidence.

These follow-up findings support the article’s short method-provenance paragraph. The table remains a list of documented community derivatives, not a claim that the linked demo reproduces their saved weight checkpoints.
